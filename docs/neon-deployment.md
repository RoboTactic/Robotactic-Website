# تجهيز RoboTactic على Neon وCloudflare

## الحالة الحالية

في 2026-11-11، وبعد موافقة المستخدم، طُبّقت التهيئة على قاعدة Neon الجديدة التي كانت فارغة، وأُنشئ `robotactic_app` بصلاحيات محدودة وأول Super Admin. نجح تدقيق الصلاحيات وتسجيل الدخول الحقيقي للدور عبر TLS مع التحقق من الشهادة واسم الخادم. لم تُنقل أو تُحذف بيانات Supabase. تعليمات المستخدم اللاحقة تمنع أي كتابة إضافية على قواعد البيانات أثناء فحص النسخة التجريبية.

اتصال العميل مشفّر ومتحقق منه حتى إن عرض `pg_stat_ssl` اتصال Neon الداخلي دون TLS. تقرير الأداة يفصل `session.client_tls` عن `session.backend_tls`؛ اعتماد تسجيل دخول التطبيق يتطلب تحقق TLS على اتصال العميل نفسه.

## ملف التهيئة المعروض للموافقة

`backend/database/neon-initialize.sql` ملف SQL واحد بمعاملة واحدة. يُولّد محليًا دون الاتصال بأي قاعدة:

```powershell
npm --prefix backend run db:neon:prepare
```

يتضمن الملف:

1. فحص أن الهدف Neon وأن public فارغ من الجداول والعروض والتسلسلات وأن الدور غير موجود. إذا لم تتحقق الشروط يتوقف؛ لا يحذف أو يعيد إنشاء أي كائن.
2. مخطط المشروع الحالي وجميع ترحيلاته السبعة، مع سجل `schema_migrations` لمنع إعادة تنفيذها لاحقًا.
3. بيانات التهيئة الموجودة أصلًا في المشروع: صفحة «من نحن»، مفاتيح إظهار الأقسام السبعة، والمسارات الثلاثة Drones وController وSensors بحالة coming_soon. لا يضيف مستخدم إدارة أو مشاركين أو محتوى تجريبيًا.
4. إنشاء `robotactic_app` بحالة NOLOGIN وPASSWORD NULL ودون SUPERUSER أو CREATEDB أو CREATEROLE أو REPLICATION أو BYPASSRLS أو توريث أدوار أخرى.
5. منح الصلاحيات المحددة في `runtimePermissions.sql`: 18 جدولًا، مع تقييد أعمدة INSERT وUPDATE، وسياسات RLS للدور فقط على الجداول المحمية. لا يغير سياسات الآخرين أو يوقف RLS.

PostgreSQL 16+ يمنح منشئ الدور CREATEROLE صلاحية إدارته تلقائيًا. الملف يسمح لهذا المسؤول باستخدام SET ROLE للتحقق من دور التطبيق، ويمنع توريث تلك العضوية تلقائيًا. اتجاه العضوية هو **المسؤول عضو في دور التطبيق**، ولا يصبح التطبيق عضوًا في دور المسؤول. الفحص يرفض أي عضوية تمنح التطبيق دورًا آخر أو تمنح مستخدمًا غير إداري الوصول إلى دوره.

لا يُشغَّل الملف بواسطة build أو deploy أو CI. طُبّق مرة واحدة بعد الموافقة؛ لا تعِد تشغيله. لا تشغّل seed أو أوامر إعادة ضبط القاعدة. لا توجد هجرة تلقائية لبيانات Supabase؛ بياناتها تبقى كما هي وأي استيراد لاحق يحتاج نسخة تصدير ومراجعة مستقلة.

## الاتصال الآمن والدور التشغيلي

`getDatabaseConnectionOptions` يفرض تحقق TLS لقواعد Neon حتى لو لم يوجد DATABASE_SSL، ويمنع معاملات SSL الموجودة في الرابط من تعطيل فحص الشهادة أو اسم الخادم. Neon يستخدم شهادات عامة موثوقة؛ لا تستخدم شهادة Supabase الجذرية لاتصاله. اضبط إعدادات الاتصال الحساسة في backend/.env المحلي المتجاهل أو في مدير أسرار فقط.

بعد الموافقة وتطبيق الملف:

```powershell
npm --prefix backend run db:role:audit -- --verify
```

هذه الأداة READ ONLY. تتحقق من الصلاحيات الفعلية ثم تخطط استعلامات الكتابة بـEXPLAIN دون ANALYZE؛ لا تكتب بيانات أو تستهلك أرقام التسلسلات. فحص SET ROLE بحساب التهيئة لا يثبت تسجيل الدخول بكلمة مرور الدور الجديد.

عيّن كلمة مرور عشوائية طويلة وفريدة من مدير كلمات مرور داخل جلسة psql موثوقة وباستخدام الطلب المخفي:

```text
SET password_encryption = 'scram-sha-256';
\password robotactic_app
ALTER ROLE robotactic_app LOGIN;
```

لا تكتب كلمة المرور في SQL نصي أو Git أو المحادثة أو معاملات سطر الأوامر. `\password` أمر خاص بـpsql. استخدم اتصال Neon المباشر لهذه الإدارة. لإنشاء الدور المحدود استخدم SQL المعروض؛ أدوار Neon المنشأة من الواجهة قد تحصل على neon_superuser تلقائيًا.

لإثبات تسجيل الدخول الحقيقي، خزّن RUNTIME_DATABASE_URL للدور الجديد محليًا مؤقتًا ثم شغّل:

```powershell
npm --prefix backend run db:role:audit -- --verify --runtime
```

يلزم أن تكون findings فارغة وverified وpasswordLoginVerified true. نجح التدقيق وتسجيل الدخول الحقيقي للدور. حُفظ اتصال التشغيل وكلمة مرور أول مسؤول في ملفات محلية متجاهلة بواسطة Git؛ لا تُرفقها بالتقارير أو أوامر الطرفية. Neon رفض تعيين SCRAM مجهّز مسبقًا؛ أداة التفعيل استخدمت كلمة مرور عشوائية كمعامل مربوط عبر TLS دون طباعتها أو تسجيلها.

## Hyperdrive والصور والنشر

- أنشئ Hyperdrive مخصصًا لـNeon بعد جاهزية دور التطبيق، باستخدام اتصاله **المباشر غير pooled** وTLS، مع Query caching معطّلًا. الرابط الحالي المحفوظ لفحص Neon pooled، فلا تنسخه كما هو إلى Hyperdrive.
- أُنشئ Hyperdrive باسم `robotactic-neon-preview` وضُبط HYPERDRIVE_ID للنسخة التجريبية. اتصال المصدر يستخدم `robotactic_app` وTLS، مع تعطيل Query caching.
- يبقى Worker واحد باسم robotactic، مع React/Vite عبر Static Assets وExpress تحت /api. أوامر Workers Builds موجودة في cloudflare-deployment.md.
- الصور ما زالت تستخدم Supabase Storage عبر SUPABASE_URL وSUPABASE_SECRET_KEY. التحويل إلى Neon يخص PostgreSQL؛ لا ينقل الصور. رفع الصور في النسخة التجريبية غير مفعّل لعدم توفر مفتاح التخزين. بعد إضافة السر اضبط `ENABLE_IMAGE_UPLOADS=true` وأعد البناء والنشر. انتقال الصور إلى R2 عمل منفصل.
- أُنشئ أول Super Admin بكلمة مرور عشوائية محلية؛ لا توجد بيانات دخول افتراضية في الكود. لا تعِد إنشاءه أثناء فحوص المعاينة.
- اختبر أول نسخة على workers.dev بعد جاهزية البيانات والأسرار. يبقى ربط الدومين الأساسي منتظرًا نجاح الاختبارات والموافقة.

## التحقق

اختبارات التهيئة تُشغّل على PostgreSQL محلي مؤقت، ولا تقرأ DATABASE_URL ولا تتصل بالإنتاج:

```powershell
npm test
npm run test:db-role
```

تشمل تجربة الملف الكامل بحساب غير superuser، والتحقق من الصلاحيات وRLS، ومنع صلاحيات زائدة أو عضويات إدارية للتطبيق، ورفض إعادة التهيئة وحماية البيانات الموجودة. نجحت الاختبارات السبعة المحلية لدور القاعدة. عُدّل اختبار الفريق ليختبر بنية البيانات دون تثبيت أسماء أشخاص قد تتغير؛ نجحت اختبارات الواجهة الـ35 ومسار ci:check على Windows وLinux.
